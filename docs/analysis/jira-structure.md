# Jira 구조 분석

Jira Cloud(Jira Software) 기준. 우리 서비스에서 무엇을 가져올지 판단하기 위한 분석이다. 마지막의 [MVP 범위](#mvp-범위)에 결론을 정리했다.

## 전체 구조

```
조직 (Organization)
└── 사이트 (Site)                     예: mycompany.atlassian.net
    ├── 사용자 · 그룹
    └── 프로젝트 (Project)            예: SCH
        ├── 이슈 (Issue)              예: SCH-12
        │   ├── 필드 (요약, 설명, 담당자, 우선순위 …)
        │   ├── 댓글 · 첨부파일 · 작업 로그
        │   ├── 이슈 링크 (차단, 관련, 중복 …)
        │   └── 변경 이력 (History)
        ├── 워크플로 (Workflow)       상태와 전환 규칙
        ├── 보드 (Board)              스크럼 / 칸반
        │   └── 스프린트 (Sprint)     스크럼만
        ├── 컴포넌트 (Component)      프로젝트 안의 영역 구분
        ├── 버전 (Version / Release)
        └── 권한 · 알림 설정 (Scheme)
```

- 대부분의 데이터는 **프로젝트 안에** 있다. 사용자, 그룹, 필터, 대시보드만 사이트 전체에서 공유한다.
- 화면의 중심은 **이슈**다. 보드, 백로그, 검색, 대시보드는 모두 "이슈를 어떤 조건으로 어떻게 보여주느냐"의 차이다.

## 프로젝트

| 항목 | 내용 |
|---|---|
| 프로젝트 키 | 대문자 2~10자. 이슈 키의 앞부분이 된다 (`SCH` → `SCH-1`, `SCH-2` …) |
| 템플릿 | **스크럼**(스프린트 단위 개발) / **칸반**(흐름 단위 작업) |
| 관리 방식 | **팀 관리형**(team-managed): 팀이 직접 설정, 단순 / **회사 관리형**(company-managed): 관리자가 설정을 여러 프로젝트에 공유, 복잡 |
| 프로젝트 리드 | 프로젝트 책임자. 기본 담당자가 될 수 있다 |

- 이슈 번호는 프로젝트마다 1부터 증가하며, 이슈를 다른 프로젝트로 옮기면 키가 바뀐다.

## 이슈

### 이슈 유형과 계층

```
에픽 (Epic)                  큰 기능 묶음. 여러 스프린트에 걸친다
└── 스토리 / 작업 / 버그      실제 작업 단위. 보드에 올라간다
    └── 하위 작업 (Sub-task)  작업을 더 잘게 나눈 것
```

| 유형 | 용도 |
|---|---|
| 에픽 (Epic) | 큰 목표. 하위 이슈의 진행률을 모아 보여준다 |
| 스토리 (Story) | 사용자 관점의 기능 ("사용자는 ~할 수 있다") |
| 작업 (Task) | 기능이 아닌 일반 작업 |
| 버그 (Bug) | 결함 |
| 하위 작업 (Sub-task) | 위 이슈 하나에 속한 세부 작업. 부모 없이 존재할 수 없다 |

- 계층은 기본 3단계(에픽 → 일반 이슈 → 하위 작업). 유료 플랜은 에픽 위에 단계를 더 만들 수 있다.

### 주요 필드

| 필드 | 설명 | 필수 |
|---|---|---|
| 키 (Key) | `SCH-12`. 자동 발급 | 자동 |
| 요약 (Summary) | 제목 | O |
| 이슈 유형 | 에픽, 스토리, 작업, 버그, 하위 작업 | O |
| 상태 (Status) | 워크플로의 현재 위치 | 자동 |
| 설명 (Description) | 리치 텍스트 (서식, 이미지, 멘션) | |
| 담당자 (Assignee) | 작업하는 사람 1명 | |
| 보고자 (Reporter) | 만든 사람. 기본값은 작성자 | O |
| 우선순위 (Priority) | Highest, High, Medium, Low, Lowest | |
| 레이블 (Labels) | 자유 태그 여러 개 | |
| 컴포넌트 | 프로젝트에서 미리 정한 영역 | |
| 수정 버전 (Fix Version) | 이 이슈가 들어갈 릴리스 | |
| 스프린트 | 속한 스프린트 | |
| 스토리 포인트 | 작업 크기 추정치 | |
| 부모 (Parent) | 에픽 또는 상위 이슈 | |
| 기한 (Due date) | 마감일 | |
| 생성일 · 수정일 · 해결일 | 자동 기록 | 자동 |
| 해결 (Resolution) | 완료 사유 (완료, 중복, 안 함 …). 값이 있으면 "해결됨"으로 본다 | 자동 |

- 사용자 정의 필드(Custom field)를 추가할 수 있다. 텍스트, 숫자, 날짜, 선택 목록, 사용자 등.

### 이슈에 붙는 것

| 항목 | 설명 |
|---|---|
| 댓글 | 리치 텍스트, `@멘션`, 수정·삭제 가능 |
| 첨부파일 | 파일 업로드. 설명·댓글에 이미지로 넣을 수 있다 |
| 이슈 링크 | 두 이슈의 관계. `차단함 / 차단됨`, `관련됨`, `중복`, `복제` |
| 작업 로그 | 들인 시간 기록. 원래 추정치와 남은 시간을 함께 관리 |
| 관찰자 (Watcher) | 알림을 받는 사람 |
| 변경 이력 | 어떤 필드를 누가 언제 무엇에서 무엇으로 바꿨는지 |

## 워크플로

이슈가 거치는 **상태**와 상태 사이의 **전환**을 정의한다.

```
     ┌──────────────────────────────────┐
     ▼                                  │
 [해야 할 일] ──시작──▶ [진행 중] ──완료──▶ [완료]
  To Do                In Progress       Done
```

- 상태는 세 가지 **분류(Category)** 중 하나에 속한다: `To Do`(회색), `In Progress`(파랑), `Done`(초록). 보드 열 배치, 진행률 계산은 분류 기준이다.
- 상태와 전환은 프로젝트(또는 이슈 유형)마다 추가할 수 있다. 예: `코드 리뷰`, `QA`
- 전환에 붙일 수 있는 규칙
  - **조건(Condition)**: 이 전환을 누가 할 수 있는가 (예: 담당자만)
  - **검증(Validator)**: 전환 전에 확인할 것 (예: 해결 사유 필수)
  - **후처리(Post function)**: 전환 후 자동으로 할 일 (예: 담당자 지정, 해결 값 설정)
- 팀 관리형은 "모든 상태로 자유롭게 이동"이 기본이다.

## 보드

이슈를 상태별 열(Column)로 보여주는 화면. 열은 하나 이상의 상태에 매핑된다.

| 항목 | 스크럼 보드 | 칸반 보드 |
|---|---|---|
| 작업 단위 | 스프린트 (보통 1~4주) | 끝없는 흐름 |
| 백로그 | 있음. 스프린트에 넣을 이슈를 고른다 | 선택 (기본은 보드에 바로 보임) |
| 보드에 보이는 이슈 | 진행 중인 스프린트의 이슈만 | 조건에 맞는 모든 이슈 |
| 제한 | - | 열별 WIP(진행 중 개수) 제한 |
| 대표 보고서 | 번다운 차트, 속도(Velocity) | 누적 흐름도(CFD), 사이클 타임 |

- 카드를 다른 열로 끌어다 놓으면 **상태 전환**이 일어난다. 워크플로에 없는 전환은 막힌다.
- 같은 열 안에서의 순서는 **랭크(Rank)** 로 저장되어 백로그와 보드가 같은 순서를 쓴다.
- **스윔레인(Swimlane)**: 가로 줄로 나누기. 담당자별, 에픽별, 우선순위별 등.
- 빠른 필터: 내 이슈만, 최근 수정 등 버튼 하나로 거르기.

### 스프린트 (스크럼)

```
계획(Future) ──시작──▶ 진행 중(Active) ──완료──▶ 종료(Closed)
```

- 이름, 목표, 시작일, 종료일을 가진다.
- 스프린트를 완료할 때 끝나지 않은 이슈는 **다음 스프린트나 백로그로 옮긴다.**
- 보드당 진행 중 스프린트는 기본 1개.

## 검색 · 필터 · 대시보드

| 기능 | 설명 |
|---|---|
| 기본 검색 | 프로젝트, 유형, 상태, 담당자 등을 드롭다운으로 고른다 |
| JQL | SQL 비슷한 검색 언어. 예: `project = SCH AND assignee = currentUser() AND status != Done ORDER BY priority DESC` |
| 필터 | 검색 조건을 저장한 것. 공유할 수 있고, 보드도 필터를 기반으로 만든다 |
| 대시보드 | 필터 결과를 가젯(차트, 목록, 통계)으로 모아 보여주는 화면 |

## 사용자 · 권한

```
사이트 관리자
└── 프로젝트 역할 (Role)        프로젝트마다 누구를 넣을지 정한다
    ├── 관리자 (Administrator)  프로젝트 설정 변경
    ├── 멤버 (Member)           이슈 생성 · 수정 · 전환
    └── 뷰어 (Viewer)           읽기만
```

- 권한은 "역할 → 권한" 매핑(권한 스킴)으로 정한다. 예: 이슈 삭제는 관리자만.
- 이슈 단위로 보이는 사람을 제한하는 **보안 수준**(Issue Security)도 있다.

## 알림

- 이슈가 생성·수정·전환·댓글 될 때 **보고자, 담당자, 관찰자**에게 알린다.
- `@멘션` 하면 그 사람에게 바로 알린다.
- 채널: 이메일, 앱 내 알림(벨 아이콘), 모바일 푸시.
- 사용자가 알림을 받을 이벤트를 고를 수 있다.

## 그 밖의 기능

| 기능 | 설명 |
|---|---|
| 컴포넌트 | 프로젝트 안의 영역 (`FE`, `BE` …). 컴포넌트별 기본 담당자 지정 가능 |
| 버전 · 릴리스 | 출시 단위. 버전별 이슈 진행률, 릴리스 노트 |
| 타임라인 (로드맵) | 에픽을 간트 차트처럼 기간으로 보여준다 |
| 자동화 | "이 조건이면 이렇게" 규칙. 예: 하위 작업이 모두 끝나면 부모를 완료로 |
| 연동 | GitHub, Slack 등. 커밋 메시지에 이슈 키(`SCH-12`)를 넣으면 이슈에 연결 |

## 엔티티 관계 정리

```
User ─┬─< ProjectMember >─ Project ─┬─< Issue ─┬─< Comment
      │                             │          ├─< Attachment
      │                             │          ├─< IssueLink >─ Issue
      │                             │          ├─< Watcher >─ User
      │                             │          ├─< History
      │                             │          └── parent ─ Issue
      │                             ├─< Status (워크플로)
      │                             ├─< Board ─< Column >─ Status
      │                             ├─< Sprint >─< Issue
      │                             ├─< Component
      │                             └─< Version
      └─< Notification
```

`─<` 는 일대다, `>─<` 는 다대다.

## MVP 범위

처음 만들 때 가져올 것과 미룰 것. 자세한 내용은 `design/`의 명세·정책에서 정한다.

| 구분 | 기능 |
|---|---|
| **MVP** | 프로젝트(키, 멤버), 이슈 CRUD, 이슈 유형(기본 5개 + 추가), 상태(기본 3개 + 추가), 스크럼(백로그·스프린트), 보드(드래그로 상태 변경, 순서), 담당자·우선순위·레이블·기한, 댓글, 기본 검색·필터, 고정 대시보드, 프로젝트 역할(관리자·멤버), 앱 내 알림 |
| **다음 단계** | 첨부파일, 이슈 링크, 변경 이력, 관찰자, 상태 전환 규칙, 버전·컴포넌트, 스프린트 보고서(번다운·속도), 시간 흐름 차트(누적 흐름도) |
| **미룸** | JQL, 사용자가 꾸미는 대시보드, 타임라인, 자동화, 사용자 정의 필드, 보안 수준, 외부 연동 |

- 워크플로를 고정해도 상태에 **분류(To Do / In Progress / Done)** 를 두면, 나중에 상태를 추가해도 보드·진행률 로직을 바꾸지 않아도 된다.
- 순서(Rank)는 처음부터 넣는다. 보드 드래그 앤 드롭에 바로 필요하다.
